# Единый backend: контракт и план переключения

Статус: целевая архитектура, до переключения Android. Интеграционная ветка —
`refactor/go-backend`, созданная от `main`. `feat/cross-platform` не используется;
новые desktop-клиенты в эту работу не входят. Наличие документа не означает
завершение миграции: критерии приёмки приведены ниже.

## Размещение и владение

Переносимый пакет `core/backend` не импортирует Flutter, JNI или Android. Он содержит
модель данных, ProfileRepository, SubscriptionService, ProfileCompiler,
SecurityPolicy и внутренний RuntimeCoordinator. `core` связывает пакет с mihomo
через EngineAdapter. Android загружает эту библиотеку в существующем процессе
`:remote`, отдельно от UI-процесса. Завершение Flutter отсоединяет подписчика событий,
но не закрывает backend и не отменяет его работу.

```text
Flutter UI — versioned JSON API — Go backend
                                  ├─ profiles / subscriptions / compiler / policy
                                  └─ RuntimeCoordinator
                                       ├─ EngineAdapter → mihomo
                                       ├─ TransportAdapter → external processes
                                       └─ PlatformAdapter → Android service / VPN / OS
```

NaiveProxy, OlcRTC, ByeDPI и StormDNS — внешние процессы. Их форматы и артефакты
сохраняются. Они не становятся outbound-реализациями mihomo. Общий контракт
транспорта: подготовить ресурсы, запустить, проверить, наблюдать, остановить;
операции принимают context и идентификатор поколения. Политика выбора стратегии,
резервного пробуждения и сна принадлежит координатору, а не процессному адаптеру.

Flutter хранит состояние представления и отправляет пользовательские намерения.
Экран не компилирует исполняемый план, не сохраняет альтернативную копию плана для
cold start и не запускает фоновые управляющие циклы. Kotlin выполняет платформенные
действия: запрос разрешения, foreground service, Builder VPN, передачу fd, защиту
сокетов, сведения о пакетах и события сети/экрана/Doze/revoke. Он не выбирает план,
не управляет транзакциями транспортов и не восстанавливает движок отдельным путём.

## Подготовка и исполнение

`RawProfile + Settings + PlatformCapabilities → ProfileCompiler(SecurityPolicy)
→ validated immutable RuntimePlan → RuntimeCoordinator`.

Компиляция не меняет работающий runtime. Все вложенные значения плана копируются;
наружу доступны только копии/сериализованный снимок. План имеет версию схемы,
поколение и digest содержимого. Только успешно проверенный план передаётся адаптерам.
Изменение настроек, выбора прокси или профиля создаёт следующее поколение.

Координатор — единственный владелец изменяемого состояния runtime. Он сериализует
команды и фиксацию результатов. Долгие компиляции и проверки отменяемы; результат
принимается только при совпадении operation ID и поколения. Stop/cancel/revoke
инвалидируют незавершённые результаты до выполнения очистки. Адаптеры не вызывают
управляющие методы координатора синхронно из своего обратного вызова.

Снимок различает desired (намерение пользователя), applied (последний успешно
зафиксированный план) и observed (фактическое состояние адаптеров, включая unknown
и degraded). Потеря связи не равна stopped. Ошибка отката видна как degraded,
а не как успешное применение старого плана.

## API, хранение и восстановление

JSON API v1: envelope содержит `apiVersion`, `operationId`, `method`, `params`.
Ответ содержит тот же operation ID, результат или структурированную ошибку.
Неизвестная major-версия отвергается до побочных эффектов. Повтор ID не должен
повторно выполнять завершённое намерение. Снимки и события имеют возрастающий seq;
attach атомарно даёт снимок и события после него. При переполнении очереди требуется
повторная синхронизация, события не блокируют работу VPN.

Состояние хранения v1 — атомарный документ с desired, committed generation,
планом и журналом pending operation. Новое состояние записывается в приватный
временный файл, fsync, rename, fsync каталога. Ссылка на применённый план меняется
вместе с его поколением. Транзакция: persist intent → execute → persist commit.
При ошибке — очистка и восстановление committed plan; незавершённый intent после
смерти процесса не принимается за успешно применённый план. Обычный запуск и
recovery вызывают один исполнитель плана. Неизвестная версия хранилища не
перезаписывается. Миграция legacy prefs/profiles/always-on сохраняет оригиналы до
успешной фиксации нового документа, повтор миграции идемпотентен.

Секреты и полный config не публикуются в диагностических событиях. Исполняемые
файлы выбираются из доверенного набора приложения, пути артефактов ограничены
каталогом backend. Публичные списки и проверки сохраняют ограничения URL,
DNS/IP, redirect, размера ответа, параллелизма и дедлайнов. Сценарии тестируются
локальными HTTP/SOCKS fixtures и виртуальными часами без публичных сайтов.

## Последовательность PR

Каждая этапная ветка создаётся от актуальной `refactor/go-backend`; base PR —
только она. После успешных проверок PR сливается merge-коммитом, ветка этапа
удаляется. Интеграционная ветка сохраняется, main не изменяется.

1. `docs/go-backend-architecture`: архитектура и инвентаризация сценариев.
2. `refactor/go-backend-coordinator`: переносимый пакет, API, атомарное хранилище,
   координатор, recovery и тестовый host; Go CI с race detector.
3. `refactor/go-backend-profiles`: хранилище профилей/настроек, миграция и сервис
   подписок. `refactor/go-backend-compiler`: компиляция, SecurityPolicy и
   совместимые fixtures. Разделение позволяет проверять сохранность данных
   независимо от преобразования конфигурации.
4. `refactor/go-backend-android`: EngineAdapter, внешние TransportAdapter,
   Android platform adapter, thin Flutter client, общее восстановление.
5. `refactor/go-backend-cutover`: удаление заменённых Dart/Kotlin путей,
   регрессии и Android E2E без Flutter; итоговая проверка интеграционной ветки.

Этапы могут требовать отдельных исправляющих коммитов, но не второго активного
владельца runtime. До cutover новый backend не управляет production runtime.
При cutover входы старого пути закрываются в том же PR, который включает новый.

## Приёмка

Все строки [inventory.md](inventory.md) подтверждены поведенческими проверками;
Android полностью использует Go backend; старая координация удалена. CI запускается
на этапных PR и push в интеграционную ветку: Go vet/test/race, Flutter analyze/test,
Kotlin unit tests, сборки Android ABI и emulator E2E. Портируемость проверяется
host-тестами без Android. Отдельно фиксируются НЕ выполненные проверки физического
ARM ABI, переходов реальных сетей и энергопотребления — эмулятор их не заменяет.

## Реализованный контракт первого этапа

`core/backend.Open` получает Compiler, EngineAdapter, TransportAdapter,
PlatformAdapter и Store. UI использует `Handle` с `apiVersion`, `operationId`,
`method`, `params`. Поддержаны apply/start/stop/recover, snapshot,
operation.get/operation.cancel. Submit возвращает receipt; Await отменяет только
ожидание. Явная отмена восстанавливает предыдущий план, новая команда отменяет
старый результат и не позволяет ему снова запустить runtime после Stop.

План и успешный receipt фиксируются одной записью. Хранятся 128 последних
receipt; повтор старого ID после его вытеснения не гарантирует дедупликацию.
Незавершённый receipt при восстановлении получает статус interrupted. Если ни
одного плана ещё не зафиксировано, recovery оставляет runtime остановленным.
Снимок включает instanceId для сброса клиентского курсора при смене процесса.
Subscribe отдаёт начальный снимок под той же блокировкой, что последующие события;
при потере событий сообщает resyncRequired. Очередь команд ограничена восемью
операциями, очередь подписчика — 256 событиями. Payload завершённого запроса
освобождается, в снимки и receipt конфигурация/секреты не попадают.

Этот пакет ещё не включён в Android runtime. Последующие этапы реализуют Compiler
и платформенные адаптеры, после чего удаляют старые владельцы состояния.

## Профили и подписки

`core/backend/profiles` хранит совместимый объект настроек и metadata профилей;
исходные байты лежат в приватных неизменяемых файлах по SHA-256. Сначала fsync
исходника, затем атомарная запись каталога с digest и ревизией. Поэтому прерванный
импорт не оставляет ссылку на недописанный источник, а scheduler и UI-список не
загружают все YAML в память. Неиспользуемые источники удаляются после фиксации.

Миграция не меняет legacy-файлы. Она сохраняет IDs, неизвестные поля и исходный
текст, включая испорченный legacy-кеш; исполнение такого кеша проверяет компилятор.
Отсутствующий кеш URL-профиля сохраняется как пустой исходник с его metadata,
чтобы подписка могла загрузиться позже. Новое сохранение требует валидации.
Лимит одного источника — 16 MiB, как существующий внутренний HTTP transport.
Чтение сверяет digest. Неизвестная версия хранилища не перезаписывается.

Обновление подписки фиксирует metadata и ссылку на исходник вместе, только при
совпадении ревизии. Ошибка HTTP/валидации и отмена сохраняют старую запись;
запоздавший ответ не затирает редактор. Сохранены оба префикса заголовков,
приоритет FlClashM, интервалы, userinfo, имя из Content-Disposition и newdomain.
Сервис принимает HTTP-клиент хоста, часы и события таймера; Flutter для него не
нужен. Настройка scheduler и сетевого клиента Android выполняется при cutover.
