# Журнал стабилизации Go backend

Цель: восстановить пользовательское поведение после переноса backend в Go.
Запись закрывается только после проверки исправления; наличие теста без прогона
не считается результатом. URL подписки, исходник и секреты профиля сюда не входят.

## Стенд

- Android Emulator `emulator-5554`, Android 16, x86_64, debug APK.
- До переноса: `565c97e247f3869d5fab6fe184f0052476114308`,
  `com.makriq.flclash.dev`.
- Go backend: исходная сборка `bef4712759a98ce7fb20ead0ed67f84fbef4cd57`,
  `com.makriq.flclash.backendcheck`.
- Один пользовательский профиль: 16 узлов, 5 групп, 7 правил; исходные байты
  обеих установок совпадают. SHA-256:
  `a90c7d47746326fad510aca74765a28c433ccf2104787f4a02e9ca795f71566d`.
- APK, приватные данные и артефакты находятся вне репозитория:
  `~/.local/state/flclashm-stabilization/`.
- Одновременно запускается VPN только одной установки. Debug-сборки не дают
  оснований для выводов о release-производительности и работе на ARM.

## Находки

### REG-006 — отключение валидатора при обновлении профиля

- Источник: сообщение владельца и ARM64 APK `0.3.1-diag8`.
- Host завершал `:validator` до снятия `BIND_AUTO_CREATE`, создавая окно для
  автоматического перезапуска службы и получения устаревшей привязки. Ошибка
  чтения PID могла выброситься из Android callback; отключение после подключения
  не завершало ожидание результата. Смерть до первого подключения могла вообще
  не вызвать callback и оставляла ожидание до общего таймаута.
- Исправление: bind/callback/teardown сериализованы на Android main dispatcher;
  сначала unbind, затем kill и ограниченное ожидание смерти с удержанием Binder.
  Отмена также дожидается cleanup. Привязка ограничена 10 секундами; потеря IPC
  повторяется один раз, ошибка самого профиля не повторяется. Неверный ответ
  валидатора завершает запрос ошибкой, не выбрасывает исключение в Binder thread.
- Android 16 x86_64: 8 одновременных проверок, 20 чередований корректного и
  ошибочного профиля, ещё одна корректная проверка, 10 обновлений локальной
  HTTP-подписки и восстановление после принудительной смерти валидатора прошли
  (`OK (3 tests)`, 48,701 с). Удаление тестовой подписки проверяет её ревизию.
- На прежнем `go-warm-debug-x86_64.apk` обычная последовательность тоже проходит,
  но смерть валидатора до подключения воспроизводит зависание и проваливает тот
  же тест восстановления. На исправленной версии этот тест проходит.
- Финальный debug APK с обеими Go ABI из `15dc181d`: все три регрессии вместе
  с `packagedBackendLifecycle` прошли (`OK (4 tests)`, 57,236 с). Последний
  сценарий проверяет настоящие ByeDPI/TUN, большой Binder payload, перезапуски,
  recovery, откат неверного профиля, proxy-only и закрытие контроллера при reset.
  Данные эмулятора после прогона восстановлены из предварительной копии.
- Во время проверки первой правки найден и устранён таймаут cleanup из-за
  освобождения последней сильной ссылки на Binder до уведомления о смерти.
  Этот промежуточный результат не считается успешной проверкой исправления.
- vivo V2361A, Android 16, ARM64 release `0.3.1-diag10`: обновлена отдельная
  диагностическая установка с сохранением данных. После запуска успешно
  обновлены обе реальные подписки, включая профиль из сообщения владельца;
  индикатор завершился, выбранный профиль сохранён. Ошибок разрыва валидатора
  в UI и журнале нового `:remote` не было.

### Причина потери предварительного запуска при переносе

- До переноса `MihomoEngineAdapter.setupRuntimePlan` запускал внешние узлы при
  подготовке профиля, отдельно от включения VPN. Stop приостанавливал автоматику
  резервов, сохраняя обычные узлы.
- В `a4e88342` появился общий инвариант: `Plan preparation while stopped must
  not keep external nodes alive`. В `7e3cff0d` вызов Start транспортов дополнительно
  перенесён под условие running=true. Так потеряно различие между «приложение
  открыто, профиль подготовлен, VPN выключен» и холодным восстановлением после Stop.
- Старый тест запрещал процессы при подготовке остановленного runtime; отдельный
  контракт открытия UI без VPN не проверялся. Тесты подтверждали новую модель,
  но не эквивалентность прежнему пользовательскому поведению.
- Это ошибка модели жизненного цикла при миграции. Сам язык Go и debug-режим
  не объясняют отсутствие слушателей. Долю стадий в минутном ожидании пока
  нельзя считать измеренной.

### REG-001 — неверный выбранный узел и необработанная ошибка после отката

- Класс: подтверждённый дефект Go-клиента на новом пути отката.
- Приоритет: P1, UI/переключение подключения.
- Шаги: Global → DE Naive → Start → проверить внешний IP → Locations →
  выбрать DE Agents WBStream → дождаться завершения операции.
- Факт: запуск OlcRTC завершился отказом сервера HTTP 403
  (`guests cannot create rooms`). Runtime откатился на DE Naive, но заголовок
  GLOBAL и выбранная карточка остались на DE Agents WBStream. В Flutter записано
  `uncaught Dart error: Bad state: operation failed`.
- Dashboard после перехода на него показывает фактический DE Naive; ошибка
  выделения и заголовка воспроизводится именно в списке прокси GLOBAL.
- Ожидание: UI показывает фактически применённый узел и сообщает об ошибке
  переключения; отказ сервера не превращается в необработанное исключение.
- Доказательство: применённый план поколения 13 содержит `GLOBAL: DE Naive`,
  операция apply завершена failed; UI показывает WBStream.
- Артефакт: локальный `reg-001-selection-mismatch.png` и диагностические логи.
- Статус: исправлено и проверено на пересобранном APK. GLOBAL остаётся на DE Naive
  после отказа WBStream, сообщение об ошибке видно в UI; новых необработанных
  Dart/Flutter-исключений нет. Последующий выбор DE TUIC успешно применился.
- Baseline: тот же серверный HTTP 403; необработанного `operation failed` при
  переключении в старой версии нет. Старая версия выбирает неработающий узел,
  Go возвращает прежний план — само сохранение рабочего VPN является улучшением.
- Исправление: план содержит идентификатор применённого профиля;
  проекция выбора в UI использует его подтверждённые данные во время работы VPN.
  Ошибка команды обновляет снимок и показывается пользователю. Изменять намерение
  backend или возвращать координацию в Dart не требуется.

### REG-004 — потеря подготовленного процесса при выключенном VPN

- Сценарий: подготовить обычный внешний узел без VPN, завершить его процесс,
  повторно открыть UI либо изменить выбор/режим.
- Причина: `nodesExecuting` оставался true, а проверка stopped-runtime пропускала
  наблюдение за транспортами. Быстрый путь подтверждал отсутствующий процесс.
- Исправление: Go проверяет подготовленные транспорты как running отдельно от
  остановленных движка и платформы; потеря процесса требует переустановки плана.
- Проверка: поведенческий host-тест для warm, выбора узла и live settings сначала
  упал во всех трёх сценариях, после исправления прошёл с race detector.
  Процесс действительно восстановлен, desired/applied running остались false.
- Android 16 x86_64, пересобранный debug APK: SIGKILL одного Naive и процесса UI,
  затем открытие UI при прежнем PID backend восстановили оба Naive. VPN остался
  выключен, туннель второго клиента не затронут.

### REG-005 — повторный захват VPN после переключения на другой клиент

- Источник: сообщение владельца. Причина подтверждена host-тестами.
- Причина: обработчик revoked мог перейти в recover при сохранённом разрешении
  или проигнорировать отзыв после восстановления TUN. Очередь также откладывала
  отзыв до завершения активной операции, включая собственный service recovery.
- Исправление: отзыв принимает durable Stop сразу и отменяет активную операцию;
  очередь повторяет обработку при конфликте поколений. Разрешение и наблюдение
  прежнего TUN не превращают отзыв в восстановление. Политика остаётся в Go.
- Проверка: host-тесты отзыва при сохранённом разрешении и обоих состояниях TUN,
  позднего onDestroy, холодного recovery и последующего явного Start прошли.
  Отдельно проверена отмена зависшей подготовки при restart и service recovery.
- Эти тесты проверяют состояние и эффекты, исходники приложения не читают.
- Android 16 x86_64: запущен VPN baseline-клиента при активном VPN Go-сборки.
  Android передал туннель baseline, Go сохранил desired/applied=false без pending;
  12 наблюдений за 22 с не выявили обратного захвата. После SIGKILL UI и `:remote`
  и повторного открытия Go-клиента владельцем VPN остался baseline.
  Последующий явный Start Go-клиента успешно вернул ему VPN.
- На прежнем APK тот же запуск baseline приводил к новому успешному recover
  Go-клиента и возвращению ему туннеля. ARM64 в этом прогоне не проверялся.

### REG-002 — внешние узлы не запускаются до включения VPN

- Источник: сообщение владельца, подтверждено сравнением кода и наблюдениями
  задержек на подготовленном стенде.
- Приоритет: P1, совместимость и подготовка подключения.
- Причина: `runtimeCoordinator.install` вызывает Start транспортов только при
  running=true и явно останавливает их при running=false. Старый
  `MihomoEngineAdapter.setupRuntimePlan` запускал узлы при подготовке профиля.
- Следствие: обычные Naive/ByeDPI недоступны для проверки задержки без VPN.
- Исправление: `ui.attach` разрешает подготовку в Go, команда `warm` запускает
  обычные процессы без изменения намерения включить VPN. Stop оставляет их для
  проверки задержки; reset/Close останавливают все процессы.
- Статус: исправлено и проверено на Android x86_64. При выключенном VPN
  DE Naive дал 245 мс (предыдущий прогон — 158 мс), два Naive и ByeDPI работают.
  Резервные узлы с activation=auto сохраняют правила сна из профиля.
- Дополнительный случай: отменённая подготовка и последующая смена режима могли
  пройти быстрым путём без запуска процессов. Быстрые пути теперь требуют
  подготовленных процессов; отдельный regression-тест прошёл.

### REG-003 — Start повторяет подготовку и запуск уже подготовленного плана

- Источник: сообщение владельца о задержках до минуты; причина-кандидат по коду.
- Приоритет: P1, запуск подключения.
- Факт по коду: переход stopped → running не считается resident и проходит
  cleanup/install; ByeDPI имеет foreground-бюджет подбора 15 с в тестовом профиле.
- Ограничение вывода: вклад этих стадий в конкретное минутное ожидание ещё не
  измерен; debug-режим не считается достаточным объяснением.
- Исправление: одинаковый подготовленный план переиспользуется после свежей
  проверки процессов. Потерянный процесс требует полного восстановления;
  выбранный спящий резерв также не проходит быстрым путём.
- Статус: исправлено для готового плана, проверено на Android x86_64.
  Start/DE Naive: 1,67 с вместе с CLI/ожиданием UI; внешний IP получен,
  PID обоих Naive и ByeDPI до и после совпадают. Предыдущий замер — 8,32 с.
  Это не точный инструментальный замер от касания и не гарантия времени
  холодного запуска: подбор стратегии и недоступная сеть требуют отдельного
  исследования при повторении долгого ожидания.

### OBS-006 — попытка скачать web UI с пустого URL

- Источник: сообщение владельца об ошибке UI; совпадение с этим логом пока

- Статус: исправлено в адаптере движка; тест проверяет сохранение локального
  пути, контроллера и явного URL. После пересборки и нескольких подготовок новых
  ошибок `Error downloading UI` нет; последняя прежняя ошибка — 15:54:59 UTC,
  новый лог проверен до 16:16:23 UTC.
- Исходное сообщение владельца об ошибке подключения UI пока не закрыто целиком:
  точный текст/совпадение с этим логом не подтверждены.

## Прогоны и проверки

### Подготовленные узлы и восстановление, исправленный APK

- `go vet ./...`, `go test ./...`, `go test -race ./backend/...` прошли после
  последнего изменения. Regression-тесты покрывают warm без VPN, повторный Start
  без перезапуска узла, потерянный процесс, Stop во время подготовки, применение
  настройки при незавершённой подготовке и headless recover после Stop.
- Product boundaries и base drift прошли; `git diff --check` без замечаний.
- Debug x86_64 APK пересобран и обновлён через `adb install -r -t`; профиль сохранён.
- На окончательном APK: Global → DE Naive → Start дал внешний IP за 1,67 с
  вместе с CLI; PID обоих Naive и ByeDPI совпали с PID до Start.
- После SIGKILL UI и `:remote` VPN восстановлен за 3,76 с без UI, поколение 30 → 32.
- Открытие UI после восстановления, Stop и Test latency: DE Naive — 103 мс,
