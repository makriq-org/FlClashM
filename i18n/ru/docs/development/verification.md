# Проверка

## Локальные команды

На NixOS используйте окружение из `flake.nix`:

```bash
nix develop -c make check
nix develop -c make go-check
```

`make check` проверяет границы product/base, закрепление GitHub Actions,
непрерывность релиза, base drift, тесты `test/product`/`test/tool` и выборочный
Flutter analyze. `make go-check` подготавливает vendor с патчами и выполняет
`go vet ./...`, `go test ./...`, `go test -race ./...` из `core`.
Для race detector нужен C-компилятор; он включён в Nix-окружение.

Дополнительно CI проверяет ошибки компиляции во всём `lib`:

```bash
nix develop -c flutter analyze --no-fatal-infos --no-fatal-warnings lib
```

## CI

| Workflow | Проверки |
|---|---|
| `android-base-verification.yaml` | Dart/Flutter, границы форка, Android unit-тесты, сборки ABI и эмуляторный E2E |
| `go-backend-verification.yaml` | Форматирование backend, vet, host-тесты и race detector всего `core` |
| `secret-scan.yaml` | Gitleaks по коммитам PR или push в main |

Изменения только документации пропускают тяжёлые задания. Изменения тестов и
проверочных Dart-инструментов запускают базовые проверки. Изменения runtime,
Android, зависимостей, плагинов, патчей и подготовки ядра сохраняют полную
Android-проверку: ARM64, armeabi-v7a и x86_64 в эмуляторе.

E2E использует локальные fixtures и настоящие mihomo, validator, ByeDPI и TUN.
Он проверяет большой Binder payload, перезапуски и recovery, отмену/откат,
proxy-only, reset и ошибки валидатора. Подготовка headless-сценария запускается
отдельно, чтобы включённый VPN не влиял на тестовую HTTP-подписку.
VPN-разрешение выдаётся через `ACTIVATE_VPN`; внешний сервер не нужен.
При сбое сохраняются instrumentation output, logcat, процессы и dumpsys.

Ручной запуск принимает `e2e_only`, `e2e_runner` и `backend_test`.
Дополнительные раннеры Blacksmith требуют подключения к репозиторию.
ARM64 APK доступен артефактом `android-arm64-test-apk`. Новое выполнение той же
ветки/PR на том же раннере отменяет предыдущее.

## Android-сборка

Нужны Flutter 3.47.x, Go 1.27.2, JDK 17, SDK 37.0 и NDK
`28.0.13004108`/`28.2.13676358`. На NixOS они заданы декларативно.

```bash
nix develop -c make dev
```

Для отдельной диагностической установки рядом с обычным клиентом:

```bash
nix develop
dart setup.dart android --arch arm64 --out core
ORG_GRADLE_PROJECT_backendDiagnostic=true flutter build apk --debug --target-platform android-arm64
```

Пакет `com.makriq.flclash.backendcheck` имеет отдельные данные и debug-подпись.
Вариант CI `backend_test` использует `com.makriq.flclash.backendtest`.
Для обновления локального APK с сохранением данных используйте `adb install -r -t`.

## Перед слиянием runtime и выпуском

На реальном Android проверяются Start/Stop, rule/global/direct, выбор узла,
задержки, настройки, обновление подписки, смерть UI и `:remote`, восстановление
без UI и сохранение явного Stop. Отдельно проверяются смена Wi-Fi/мобильной сети,
энергопотребление и каждый новый внешний узел на выпускаемых ARM ABI.
Успех сборки или x86_64 E2E не заменяет эти прогоны.

Из диагностики 21–23 октября 2026 остаются проверки и замечания:

- После импорта список прокси мог ждать подготовки внешних узлов. Нужно замерить
  холодный запуск и недоступную сеть по стадиям; быстрый готовый Start не закрывает
  этот случай.
- Спящие `activation: auto` узлы показывали Timeout при проверке задержки.
  Нужно различить сон и отказ и определить поведение ручной проверки.
- На ARM64 наблюдался таймаут рукопожатия OlcRTC/VK. Причина на стороне клиента,
  сети или сервера не установлена; успешная прямая проверка Naive не закрывает
  полный путь через mihomo. Нужно исключить конфликт портов соседних установок.
- При неудачном переключении UI показывал `Bad state: operation cancelled`,
  а foreground-уведомление менялось нестабильно. Нужны понятная локализованная
  ошибка, результат последнего выбора и проверка отмены/отката уведомления.
- Ошибка загрузки web UI с пустым URL исправлена. Совпадение с исходной жалобой
  на подключение UI не подтверждено; при повторении нужен точный текст.

Эти пункты не считаются закрытыми удалением рабочих отчётов. Старые замеры,
частные логи и история исправлений доступны в истории Git; здесь хранится
только актуальный порядок проверки и незакрытые вопросы.
