# ✅ Проверка сборки

## 🤖 CI-проверка

`.github/workflows/android-base-verification.yaml` проверяет:

- 🚧 границы продуктового слоя;
- 📦 контракт релизов;
- 🔄 расхождения base-файлов с `upstream/dev`;
- 🧪 тесты `test/product` и `test/tool`;
- 🔒 закрепление внешних GitHub Actions за полными commit SHA;
- 🔍 выборочный статический анализ продуктового и выпускного кода;
- 🏗 Android-сборку для `arm64`.

> [!NOTE]
> При изменении Android/runtime-пути дополнительно собирается `armeabi-v7a`, а `x86_64` запускается на Android Emulator. Эмулятор запускается и при изменении Dart-моста между UI и backend (`lib/product/{android,backend,bootstrap,runtime}/**`, `lib/clash/**`, `lib/{application,controller,main,state}.dart`), потому что E2E открывает настоящую Flutter-activity.

Изменения только в Flutter-тестах, проверочных инструментах, настройках анализа или changelog запускают базовые проверки без сборки APK. Изменения зависимостей, локальных плагинов, патчей ядра и инструментов подготовки runtime сохраняют полную Android-проверку. Android unit-тесты выполняются отдельным заданием параллельно сборке ARM64 APK.

Во всех Android-заданиях включён кеш результатов задач Gradle. Кеш обновляется на доверенных ветках и внутренних PR; PR из форков используют его только для чтения. Android-кеш Go отделён от host-проверок и разделён по ABI и версиям инструментов; изменения исходников и патчей создают новую запись с возможностью восстановить предыдущий кеш той же версии зависимостей.

Для сравнения раннеров ручной запуск workflow принимает `e2e_runner`: `ubuntu-latest` (по умолчанию), `blacksmith-4vcpu-ubuntu-2404` или `blacksmith-8vcpu-ubuntu-2404`. Blacksmith предварительно подключается к организации и репозиторию. Для замера только E2E без повторения остальных сборок включается `e2e_only`; этот параметр действует только при ручном запуске. Автоматические PR/push-проверки продолжают использовать GitHub. Сравнивать нужно один commit SHA: первый запуск каждого раннера учитывать отдельно как прогрев, затем выполнить по три последовательных прогона и сравнить медиану времени E2E-задания, сборки APK и запуска эмулятора. Общая длительность workflow также учитывает остальные Android-задания, оставшиеся на GitHub. Разные раннеры можно сравнивать параллельно; повторы на одном раннере выполнять последовательно: concurrency отменяет предыдущий незавершённый запуск той же ветки на том же типе раннера.

Эмуляторный E2E устанавливает debug APK, проверяет наличие всех упакованных runtime-бинарников и работает через production Go API в процессе `:remote`. Основной сценарий импортирует локальный профиль больше лимита Binder-транзакции с ByeDPI-узлом и правилом `MATCH,REJECT`, запускает настоящие `:validator`, ByeDPI, TUN и foreground-службу и проверяет, что скомпилированные правила дошли до ядра. Затем проверяются перезапуски, восстановление по сохранённому состоянию, откат ошибочного редактирования, proxy-only режим и закрытие контроллера при сбросе данных. Отдельные тесты покрывают повторные проверки профиля в `:validator`, его восстановление после смерти, обновления локальной HTTP-подписки и переподключение Binder после гибели `:remote`. Системное VPN-разрешение выдаётся через `ACTIVATE_VPN`: это единственная тестовая предпосылка, потому что системный consent UI намеренно не автоматизируется. Внешняя сеть тесту не нужна: правило `MATCH,REJECT` отклоняет весь трафик внутри VPN.

После основного набора скрипт открывает настоящую Flutter-activity и выполняет фазы `seed`, `observe`, `recovered` только для `packagedBackendLifecycle`. Проверяется, что после SIGKILL процесса UI `:remote` сохраняет PID и VPN работает дальше, а после SIGKILL `:remote` без UI Android перезапускает sticky foreground-службу, Go recovery применяет новое поколение плана без незавершённых операций, и только затем UI открывается снова. Скрипт падает, если instrumentation сообщает об ошибке или аварии либо в `logcat` есть необработанное исключение Flutter.

При падении workflow сохраняет instrumentation output, `logcat`, список процессов и срезы `dumpsys` для служб, VPN-сети и уведомлений. Проверка покрывает Android-контракт на `x86_64`; работоспособность runtime-бинарников на ARM ABI по-прежнему подтверждается перед выпуском на реальном устройстве.

**Как запускается.** Для рабочих веток основной процесс запускается событием pull request, а `push` используется только для `main` и `dev`. Отдельный `go-backend-verification` при изменениях `core/**` и подготовки ядра выполняет `gofmt`, `go vet`, host-тесты и race detector без Android; триггеры у него те же. Отдельный процесс непрерывности выпуска оставлен для ручного запуска: автоматически эта проверка уже входит в основной процесс, поэтому один коммит не создаёт дублирующие наборы проверок. Новый запуск того же pull request отменяет предыдущий незавершённый. Если изменена только посторонняя документация, тяжёлые задания пропускаются.

Отдельный `secret-scan` проверяет Gitleaks все коммиты, добавленные pull request или push в `main` и `dev`. Версия сканера и SHA-256 его архива зафиксированы в workflow.

## 💻 Локальная проверка

```bash
flutter pub get
dart tool/check_product_boundaries.dart
dart tool/check_actions_pinning.dart
dart tool/check_release_continuity.dart
dart tool/check_base_drift.dart
flutter test test/product test/tool
flutter analyze --fatal-infos lib/product test/product test/tool
```

## 📱 Android-сборка

Нужны: Android SDK 37.0, NDK `28.0.13004108` + `28.2.13676358`, JDK 17.

```bash
flutter pub get
dart setup.dart android --arch arm64 --out core
flutter build apk --release
```

> [!WARNING]
> Эмуляторный E2E не заменяет предрелизную проверку ARM ABI на реальном Android-устройстве.
