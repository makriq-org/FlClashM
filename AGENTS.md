# AGENTS.md

Правила работы с репозиторием `FlClashM`. Пометка **⚙️ CI** — проверяется автоматикой,
ломать нельзя.

## Контекст

- **Проект:** `FlClashM` — Android-клиент для `mihomo`, форк `FlClashX`.
- **Режим:** `maintenance/cheap-upstream` — минимум расхождений с апстримом.
- **`applicationId`:** `com.makriq.flclash` — не менять (⚙️ CI).
- **Релизный канал:** `makriq-org/FlClashM`.

## Принципы

- Кратко и по существу. Простые, предсказуемые, обратимые решения.
- Продуктовую логику не размазывать по базе без явной архитектурной причины.
- Перед новой runtime-интеграцией зафиксировать: место в архитектуре, контракт,
  ограничения безопасности, путь обновления и отката.

## Архитектура

Главная цепочка:

```
RawProfile → ProfileCompiler → SecurityPolicy → RuntimePlan → EngineManager → EngineAdapter
```

Слои:

1. **FlClashX Base** — интерфейс, навигация, базовый runtime path.
2. **Product Layer** (`lib/product/**`) — форковая логика, политика безопасности,
   обновления, fork-only страницы.
3. **Runtime Layer** — `mihomo` (базовый) + встроенные узлы `naiveproxy`, `olcrtc`, `byedpi`, `stormdns`.
4. **Platform Layer** — Android VPN, foreground service, installer bridge.

**Граница base ↔ product (⚙️ CI):**

- Base-код вне `lib/product/**` знает о product-слое только через разрешённые
  touchpoints из `tool/product_touchpoints.json`.
- Живые `lib/views/**` не копируются в product-слой — остаются файлами апстрима с
  минимальными зарегистрированными хуками.
- Fork-only страницы держать в `lib/product/pages/**` с тонким mount-файлом в базе,
  и только когда без него страница недостижима.
- Любой файл в `lib/product/**`, объявляющий виджет или фабрику `Widget`, должен иметь
  запись с причиной в `allowedProductUi` (`tool/product_touchpoints.json`).
- Любое изменение base-файла вне `lib/product/**` — только через product layer +
  запись в `product_touchpoints.json`, либо осознанная запись в
  `tool/base_drift_allowlist.json`. Проверяет `dart tool/check_base_drift.dart`.

## Ветки

`тип/короткое-имя` в нижнем регистре через дефис, латиницей. Типы (общий словарь для
веток, коммитов, PR и issue):

| Тип | Назначение |
|---|---|
| `feat` | новая функциональность |
| `fix` | исправление бага |
| `perf` | оптимизация без смены поведения |
| `refactor` | переработка без смены поведения |
| `docs` | только документация/README/CHANGELOG-текст |
| `build` | сборка, зависимости, CI |
| `chore` | инфраструктура, уборка (пользователь не заметит) |
| `release` | подготовка выпуска (версия, changelog, шаблоны) |

Пример: `feat/olcrtc-auto-activation`. Прямой push в `main` запрещён — только через PR.

### Desktop-направление

- `feat/cross-platform` — постоянная интеграционная ветка desktop-направления. Пока
  направление активно, ветку не удалять, даже если её текущая вершина уже входит в
  `main`.
- Этапы работы ответвляются от `feat/cross-platform`, а их PR направляются обратно в
  неё. После слияния удаляется только ветка этапа.
- Первый этап — `feat/platform-composition`.

## Issue

Правила FlClashM; формы в `.github/ISSUE_TEMPLATE/` должны им соответствовать.
Одна issue — одна проблема или один проверяемый результат. Перед созданием проверить
дубликаты; связанные задачи связать ссылками, большую работу разбить на подзадачи.

### Заголовок и описание

- **Заголовок:** `тип: суть`, на русском, без точки, ≤ 72 символов. Тип — из общего
  словаря выше. Префиксы `[BUG]` и `[Feature]` больше не использовать.
- Баг описывать как наблюдаемую проблему в настоящем времени; предложение или задачу —
  как требуемое действие в неопределённой форме. Прошедшее время относится к коммитам
  и PR, где изменение уже сделано.

  ```
  fix: VPN не восстанавливается после смены сети
  feat: добавить поиск по профилям
  refactor: выделить адаптер desktop runtime
  build: сократить время проверки Go backend в CI
  ```

- **Описание:** на русском, кратко и по существу. Для бага — что происходит,
  как повторить и что ожидается; для предложения или задачи — зачем это нужно,
  что требуется и как проверить результат. Короткие issue не требуют заголовков
  для каждого абзаца. Не повторять одну мысль в нескольких разделах.
- Окружение и диагностику указывать по необходимости. Версию приложения, ОС,
  устройство, ABI и логи запрашивать, только когда они помогают разбору.
  Не добавлять пустые анкеты и списки «не указано».
- Для новой runtime-интеграции дополнительно описать место в архитектуре, контракт,
  безопасность, обновление и откат по разделу «Принципы».
- Перед публикацией логов и вложений удалить подписки, токены, ключи, пароли
  и персональные данные. Отсутствие логов само по себе не повод закрывать issue.

### Метки

У обычной issue **ровно три метки в порядке: тип → приоритет → объём работы**.
GitHub сортирует метки по имени: префиксы `1 ·` у типа и `2 ·` у приоритета
обеспечивают порядок `1 · Ошибка` → `2 · Приоритет: средний` → `Объём: малый`.
У меток объёма числового префикса нет; это общий словарь для issue и PR.
Названия и цвета одинаковы у открытых и закрытых issue. Области и статусы отдельными
метками не отмечать. Метки назначает сопровождающий; формы их не добавляют.
Неиспользуемые метки можно удалять из GitHub; при необходимости создавать заново
по словарю и цветам ниже.

| Тип заголовка | Метка | Цвет (HEX) |
|---|---|---|
| `fix` | `1 · Ошибка` | `d73a4a` |
| `feat` | `1 · Функция` | `2da44e` |
| `perf` | `1 · Оптимизация` | `008672` |
| `refactor` | `1 · Рефакторинг` | `8250df` |
| `docs` | `1 · Документация` | `0969da` |
| `build` | `1 · Сборка` | `d4a72c` |
| `chore` | `1 · Обслуживание` | `6e7781` |
| `release` | `1 · Релиз` | `bc4c00` |

| Метка приоритета | Когда использовать | Цвет (HEX) |
|---|---|---|
| `2 · Приоритет: не задан` | решение об очерёдности ещё не принято | `ededed` |
| `2 · Приоритет: высокий` | критическая проблема или блокирующая задача | `b60205` |
| `2 · Приоритет: средний` | обычная запланированная работа | `fbca04` |
| `2 · Приоритет: низкий` | можно отложить без существенного ущерба | `c2e0c6` |

| Метка объёма | Оценка работы вместе с проверкой | Цвет (HEX) |
|---|---|---|
| `Объём: не оценён` | данных для оценки пока недостаточно | `ededed` |
| `Объём: малый` | локальная правка с понятной проверкой | `bfd4f2` |
| `Объём: средний` | несколько связанных изменений или сценариев проверки | `6f9de2` |
| `Объём: большой` | несколько этапов, архитектурные изменения или миграция | `8250df` |

- Приоритет и объём оценивать независимо, по содержанию задачи, не по её типу
  или числу реакций. Не выдавать предположение за согласованную оценку; при
  неопределённости использовать «не задан» / «не оценён». Большую работу делить
  на связанные подзадачи. Срок или целевой выпуск указывать через milestone.
- При смене оценки старую метку заменять. Новые значения сначала согласовать
  в `AGENTS.md`.

### Разбор и закрытие

- При нехватке сведений запросить конкретные данные; ошибки оформления сначала
  исправить. Дубликат закрывать со ссылкой на основную issue, отказ — с причиной.
- PR связывать через `Fixes #123` / `Closes #123`, если выполнены все критерии;
  для частичной работы — `Refs #123`. После слияния в `dev` или интеграционную
  ветку проверить закрытие вручную.
- Закрывать выполненную задачу после слияния и проверки результата, со ссылкой
  на PR/коммит. Все три метки сохранять. Текущую работу и блокирующие зависимости
  пояснять в комментариях по необходимости.
- Панель Renovate — служебная сводка, исключение из правил обычных задач:
  - стабильный заголовок из опубликованного `renovate.json5`, без ручного переименования;
  - закреплена над списком issue;
  - единственная метка `🤖 Renovate`, цвет `7057ff`; тип, приоритет и объём не нужны;
  - короткое вступление с пометкой «Служебная панель», далее — сводка бота;
  - генерируемые разделы, их язык и служебные переключатели сохранять.
  Заголовок не менять вручную: рассогласование с конфигурацией создаёт дубликат.
  Панель остаётся открытой на время использования Renovate; оценка работы и
  критерии готовности относятся к отдельным задачам и PR обновлений.

## Коммиты

Формат заголовка: **`тип: описание`**

- русский, **прошедшее время / результат** («что стало»), без точки, ≤ 72 символов;
- одна логическая правка = один коммит;
- без AI-трейлеров (`Co-Authored-By` от Claude/Codex).

```
feat: добавлена кнопка x86_64 в описание пре-релиза
fix: восстановлена foreground-служба после перезапуска процесса
chore: обновлён Go до 1.26 и зависимости ядра
```

Тело (после пустой строки) — когда нужно объяснить *почему* или есть несовместимость.
Ломающее изменение помечать строкой `BREAKING: …`. Заголовок и тело — **всегда на русском**.

## Pull Request (PR)

- **Заголовок** = `тип: суть` (тот же тип, что у ветки). Заголовок и описание — **всегда на русском**.
- **Описание** по шаблону:

  ```
  ## Зачем
  Проблема/причина в 1–2 предложениях.

  ## Что сделано
  - ключевые изменения списком

  ## Как проверено
  - flutter analyze / тесты
  - ручная проверка (что именно)

  ## Влияние на пользователя
  CHANGELOG обновлён / не требуется · есть BREAKING / нет
  ```

- **Метки открытого PR:** ровно две — тип из общего словаря (например,
  `1 · Ошибка`) и `Объём: малый` / `Объём: средний` / `Объём: большой`.
  Тип соответствует заголовку; приоритет остаётся у issue. Это относится также
  к draft и автоматическим PR. У объёма нет числового префикса, поэтому тип
  отображается первым.
- **Оценка объёма:** изучить diff относительно целевой ветки и необходимые проверки.
  Оценивать конкретное изменение вместе с ревью, сборкой, проверкой платформ/ABI,
  установки, отката и совместимости. Не копировать объём связанной issue и не
  определять его только по числу строк или файлов. `Объём: не оценён` допустим
  временно, пока не изучено содержание; при разборе заменить реальной оценкой.
- Открытые PR размечать при создании или первом разборе; после существенного
  обновления diff пересматривать оценку и заменять старую метку. При закрытии
  назначенные метки сохранять. Исторические закрытые PR массово не размечать
  и не переоценивать. Renovate автоматически назначает только тип; объём
  оценивается по содержанию конкретного PR, без фиксированного значения по умолчанию.

- **Мердж:** merge-commit; squash — если рабочие коммиты хранить не нужно.

## CHANGELOG

- Новые пункты копятся в секции `## Unreleased`, строками `- …`.
- Каждый пункт: **одно** изменение с точки зрения пользователя, начинается с глагола,
  ≤ ~100 символов (одна строка), без внутренних терминов и имён классов.
- Чисто внутренние правки (CI, рефактор без видимого эффекта) в changelog не пишем.

```
✅ Ограничен расход памяти в списках прокси, логах и соединениях.
❌ Рефакторинг product_runtime и алфавитная сортировка экспортов.
```

- **⚙️ CI:** при выпуске секция получает заголовок, **точно равный тегу** (`## v0.11.0-pre1`).
  Сборка извлекает этот блок; нет секции — билд падает. В описание релиза и окно обновления
  попадают только строки `- …`.

## Версии

`pubspec.yaml → version: MAJOR.MINOR.PATCH[-preN]+ГГГГММДДnn`
(полный versionName + versionCode).

**versionName — SemVer.** Что поднимаем:

| Двигаем | Когда |
|---|---|
| **MAJOR** | несовместимое изменение: формат профиля/конфига, миграция данных, удаление функции или настройки, смена схемы обновлений |
| **MINOR** | новая функция, обратно совместимо |
| **PATCH** | багфиксы и мелочи |

- В релизе несколько типов → берём старший; `BREAKING:` → обязателен MAJOR.
- Поднимаем только одну позицию, младшие обнуляем (`0.10.6` → `0.11.0`).
- Изменения апстрима при синхронизации тоже учитываем при выборе уровня повышения версии по их эффекту
  для пользователей FlClashM. Версию FlClashX в наш versionName не переносим.

**Пре-релизы — линейные `-preN`:** `0.11.0-pre1`, `-pre2`, … Суффикс входит в
`versionName` в `pubspec.yaml`; счётчик обнуляется только при переходе к новой целевой
версии. Стабильный выпуск = тот же versionName без суффикса.

**versionCode — `ГГГГММДДnn`** (дата сборки + счётчик за день с `01`):

- при каждом теге должен строго вырасти (**⚙️ CI:** `versionCode` строго больше нижней границы);
- pre и stable одной версии имеют разные versionCode (stable всегда позже → больше).

**⚙️ CI — тег ↔ версия:** тег обязан точно совпадать с полным versionName из
`pubspec.yaml`: `v{versionName}`. VersionName поднимаем **до** тега.

## Релиз

Ветка `release/<версия>` (напр. `release/v0.11.0-pre1`):

1. Перенести пункты из `## Unreleased` в секцию с заголовком, равным будущему тегу
   (`## v0.11.0-pre1`).
2. Поднять версию в `pubspec.yaml`: versionName по таблице + новый versionCode.
3. Локально прогнать `dart tool/check_release_continuity.dart` и `flutter analyze`.
4. PR → merge в `main` (заголовок `release: v0.11.0-pre1`).
5. Поставить тег `v0.11.0-pre1` **на влитый в `main` коммит** и запушить. `build.yaml`
   собирает APK/AAB, подставляет `VERSION/TAG/REPO/{{CHANGES}}` в `pre_release_template.md`
   (pre) или `release_template.md` (stable) и публикует релиз + каталог обновлений.
6. Пре-релизы встроенный апдейтер не показывает, пока пользователь не включит их в
   настройках; стабильные видны всем.

Стабильный выпуск — то же, но заголовок секции, ветка и тег без суффикса (`v0.11.0`),
шаблон `release_template.md`. **Теги — только на коммиты в `main`.**

## Синхронизация с апстримом

Обновление вести от `upstream/dev`:

1. `git fetch upstream && git fetch origin`.
2. Ветку от целевой ветки форка → `git merge upstream/dev`, разрешить конфликты
   (Dart-пакет форка называется `flclashx`, как в апстриме — нормализация импортов не нужна).
   Для типовых конфликтов включён `rerere`: после первого ручного разрешения Git подставит
   сохранённый вариант.
3. Сразу проверить base-дрейф: `dart tool/check_base_drift.dart` (сравнивает дерево с
   merge-base относительно `upstream/dev`; без `upstream` передать `--merge-base=<sha>` или
   `BASE_DRIFT_MERGE_BASE`).
4. Финальные проверки: `dart tool/check_product_boundaries.dart`, `flutter test test/product`,
   `dart tool/check_base_drift.dart`. Новый base-путь → сначала вынести в touchpoints или
   осознанно добавить запись в `base_drift_allowlist.json` с причиной, потом завершать синк.
5. Синк без изменений, заметных пользователю, отдельного релиза не требует и входит в
   ближайший выпуск. Синк, затрагивающий runtime path, сначала проводить через `-preN`
   с проверкой на реальных Android ABI.

## Ограничения

- В дереве ещё есть legacy desktop/base код — не цель релизов.
- Часть UI/lifecycle wiring идёт через legacy `GlobalState`/controller — не ломать baseline
  при чистке.
- Cold-start и runtime-node path проверять на реальных Android ABI после каждой новой
  встроенной ноды.
