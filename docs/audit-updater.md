# Аудит встроенного апдейтера

## Вердикт

Не работает как надёжный встроенный канал обновления для уже выпущенных сборок. Основная причина не в скачивании APK, не в сверке SHA256 и не в запуске установщика. Главный разрыв в том, что уже выпущенные клиенты и реальный выпуск релизов некоторое время жили по разным правилам. Стабильные сборки до текущей ветки смотрели только `releases/latest`, а после `v0.10.2` в репозитории публиковались только предвыпуски `v0.10.3-pre1` ... `v0.10.4-pre2`. Предвыпуски до `v0.10.3-pre4` вообще выходили из проверки обновлений по `globalState.isPre`, поэтому для них загрузчик был фактически выключен. В текущем `main` эти два разрыва уже закрыты, но в коде остался частный дефект с запасным `universal.apk`.

## Доказательства

### Реальные релизы

`gh release list -R makriq-org/FlClashM --limit 20` показал, что на `2026-07-06` последний стабильный тег это `v0.10.2` от `2026-05-29`, а все более новые теги это предвыпуски `v0.10.3-pre1` ... `v0.10.4-pre2`, последний из них опубликован `2026-06-22`. Для `v0.10.2` и `v0.10.4-pre2` реальные APK-ассеты названы одинаково: `FlClashM-android-universal.apk`, `FlClashM-android-arm64-v8a.apk`, `FlClashM-android-armeabi-v7a.apk`, `FlClashM-android-x86_64.apk`, плюс `FlClashM-android-release.aab` и `FlClashM-android-release-metadata.json`.

Для `v0.10.2` рядом лежат sidecar-файлы `.sha256`. Для `v0.10.4-pre2` sidecar-файлов уже нет, но сам ответ GitHub API содержит `digest: "sha256:..."` у каждого APK. Это подтвердилось и через `gh api`, и через обычный `curl -s https://api.github.com/repos/makriq-org/FlClashM/releases?per_page=2 | jq '.[0].assets[] | {name, digest}'`.

Содержимое реального sidecar у стабильного релиза соответствует ожиданию парсера. Например, `FlClashM-android-arm64-v8a.apk.sha256` из `v0.10.2` содержит строку `0ca90e4a6c67456d11b7d486757147f4564a6f562c3aaa37d149db63115f8c12  ./FlClashM-android-arm64-v8a.apk`. Парсер принимает такой формат, потому что умеет брать имя файла из последнего сегмента пути в `lib/product/services/app_update_release.dart:256-263`.

### Выбор ассета

Текущий выбор APK идёт по `selectAndroidReleaseAsset` в `lib/product/services/app_update_release.dart:115-152`. Реальные ABI-суффиксы релизов совпадают с тем, что Android обычно возвращает через `supportedAbis`: `arm64-v8a`, `armeabi-v7a`, `x86_64`. Значит для обычных ARM и `x86_64` устройств выбор совпадает с реальными именами ассетов.

При этом `FlClashM-android-universal.apk` парсится не как отдельный запасной файл, а как ABI `universal`, потому что шаблон имени в `lib/product/services/app_update_release.dart:21-38` считает любой суффикс после `-android-` значением ABI. Из-за этого запасной путь `universalAsset` в `lib/product/services/app_update_release.dart:120-150` фактически не срабатывает для реального имени `FlClashM-android-universal.apk`.

### SHA256

Путь проверки в текущем коде выглядит корректно. `AppUpdateService` сначала пытается взять встроенный `sha256:` из метаданных ассета, а потом только sidecar `.sha256`, что видно в `lib/product/services/app_update_service.dart:170-190`. Это согласовано с реальными релизами: стабильные теги дают и `.sha256`, и `digest`, предвыпуски дают хотя бы `digest`.

Рабочий процесс публикации сейчас генерирует `.sha256` только для стабильного канала. Это видно в `.github/workflows/build.yaml:227-233`, где шаг `Generate sha256` обёрнут условием `if: env.IS_STABLE == 'true'`. Поэтому текущий предвыпускной канал зависит от поля `digest` в GitHub API, а не от собственного sidecar-файла.

### Сверка версий

Текущий `main` уже выбирает релиз через общий список `releases?per_page=20` и умеет фильтровать предвыпуски флагом `includePrerelease`, что видно в `lib/product/android/android_update_bridge.dart:85-114` и `lib/product/services/app_update_release.dart:199-214`. Сравнение версий в `lib/common/utils.dart:396-495` корректно срезает префикс `v`, понимает `-pre`, `-pre2`, `-pre10` и считает стабильную `0.10.4` новее, чем `0.10.4-pre2`.

Но уже выпущенный стабильный клиент `v0.10.2` работал иначе. В `v0.10.2:lib/product/android/android_update_bridge.dart:70-82` запрос шёл только в `https://api.github.com/repos/$repository/releases/latest`, то есть только в последний стабильный релиз. Пока после `v0.10.2` публиковались только предвыпуски, такой клиент не мог увидеть ни `v0.10.3-pre*`, ни `v0.10.4-pre*`.

Ещё жёстче ситуация была у выпущенных предвыпусков до `v0.10.3-pre4`. В `v0.10.2:lib/product/services/app_update_service.dart:27-50` и автоматическая, и ручная проверка сразу выходят при `globalState.isPre`. Коммит `a149b07` убрал этот разрыв и добавил поддержку `includePrerelease`; `git tag --contains a149b07` показывает, что исправление попало только в `v0.10.3-pre4`, `v0.10.3-pre5`, `v0.10.3-pre6`, `v0.10.4-pre1`, `v0.10.4-pre2`.

### Установка

Цепочка установки по коду согласована. APK скачивается в `homeDir/updates` через `lib/product/android/android_update_bridge.dart:296-301`. `homeDir` берётся из `getApplicationSupportDirectory()` в `lib/common/path.dart:15-18,65-68`, то есть это внутренний каталог приложения. `FileProvider` объявлен с authority `${applicationId}.fileProvider` в `android/app/src/main/AndroidManifest.xml:166-174`, сам `applicationId` закреплён как `com.makriq.flclash` в `android/app/build.gradle.kts:42-48`, а `file_paths.xml` открывает весь внутренний каталог `files-path path="."` в `android/app/src/main/res/xml/file_paths.xml:1-5`. Kotlin-мост действительно строит тот же authority `${appContext.packageName}.fileProvider` и запускает `ACTION_INSTALL_PACKAGE` в `android/app/src/main/kotlin/com/follow/clashx/plugins/AppPlugin.kt:257-307`. Разрешение `REQUEST_INSTALL_PACKAGES` присутствует в `android/app/src/main/AndroidManifest.xml:19`.

## Найденные разрывы

### Разрыв: стабильный клиент видел только стабильные релизы

Где ломает: `v0.10.2:lib/product/android/android_update_bridge.dart:70-82`.

Почему ломает: клиент спрашивал только `releases/latest`, а реальная публикация после `v0.10.2` шла только в предвыпуски. Для пользователя это выглядит как отсутствие обновлений, хотя новые теги в репозитории уже есть.

Тяжесть: критично для канала обновления стабильных пользователей.

### Разрыв: предвыпуски до `v0.10.3-pre4` вообще не проверяли обновления

Где ломает: `v0.10.2:lib/product/services/app_update_service.dart:27-50`.

Почему ломает: и авто-проверка, и ручная проверка возвращались сразу при `globalState.isPre`. Для пользователя на таких тегах загрузчик действительно отсутствовал функционально.

Тяжесть: критично для пользователей `v0.10.3-pre1`, `v0.10.3-pre2` и `v0.10.3-pre3`.

### Разрыв: `universal.apk` не работает как запасной ассет

Где ломает: `lib/product/services/app_update_release.dart:122-150`.

Почему ломает: реальный файл называется `FlClashM-android-universal.apk`, но код трактует `universal` как обычный ABI и не кладёт этот файл в `universalAsset`. Если устройство вернёт ABI, для которого нет точного совпадения в релизе, запасной переход на universal не произойдёт.

Тяжесть: средне. На обычных `arm64-v8a`, `armeabi-v7a` и `x86_64` это не мешает, но контракт запасного APK сейчас формально сломан.

### Разрыв: предвыпуски зависят от `digest` GitHub API

Где ломает: `.github/workflows/build.yaml:227-233`.

Почему ломает: sidecar `.sha256` публикуется только для стабильного канала. Предвыпускной канал живёт только за счёт поля `digest` в ответе GitHub API. На `2026-07-06` это поле реально приходит, поэтому прямой сбой не воспроизвёлся, но для security-critical части контракта это лишняя внешняя зависимость.

Тяжесть: средне.

## Предлагаемый фикс

Для первого разрыва минимальный рабочий путь не в новой правке текущего `main`, а в выпуске нового стабильного тега с уже исправленным апдейтером из текущей ветки. Иначе клиенты `v0.10.0` ... `v0.10.2` так и останутся на стабильном канале `v0.10.2`, потому что новее стабильного релиза они не увидят. Отдельная задача должна подготовить и выпустить ближайший стабильный тег из текущего `main`.

Для второго разрыва код в `main` уже исправлен коммитом `a149b07` и последующими изменениями в `lib/product/android/android_update_bridge.dart`, `lib/controller.dart`, `lib/views/about.dart` и `lib/models/config.dart`. Дополнительной кодовой правки не требуется; нужен выпуск и явное сообщение пользователям `v0.10.3-pre1` ... `v0.10.3-pre3`, что перейти на новую ветку они смогут только ручной установкой APK, потому что их собственный загрузчик не починить удалённо.

Для третьего разрыва минимальная правка нужна в `lib/product/services/app_update_release.dart`. Реальный `FlClashM-android-universal.apk` надо явно считать запасным универсальным файлом, а не обычным ABI. Достаточно распознать суффикс `universal` отдельно и сохранять такой ассет в `universalAsset`.

Для четвёртого разрыва минимальная правка нужна в `.github/workflows/build.yaml`. Шаг `Generate sha256` надо выполнять и для стабильных, и для предвыпускных релизов, то есть убрать условие `if: env.IS_STABLE == 'true'`. Тогда клиент сможет брать контрольную сумму либо из sidecar, либо из `digest`, а контракт проверки не будет зависеть только от поля GitHub API.

## Что не удалось проверить

Не запускал фактическую установку APK на реальном Android-устройстве и не проверял системный экран разрешения на установку из неизвестного источника. По статическому разбору authority, путь файла и `FileProvider` согласованы, но конечное поведение интента `ACTION_INSTALL_PACKAGE` на устройстве я не воспроизводил.
